A. Bug (sudah diverifikasi)
B1 · Harvest yang terlampir Delivery Request bisa ikut rute armada → ajuan macet permanen
Prioritas: Tinggi   ·   Lokasi: app/routers/factory.py — POST /factory/dispatch (±baris 85–125); app/services/factory_ops.py — submit_request (±baris 72–80)
Masalah
Dispatch hanya memeriksa status 'verified', tidak memeriksa delivery_request_id. Terbukti dengan tes: harvest dilampirkan ke DR → dispatch 201 → diterima via rute (tagihan rute Rp 499.100) → QC lot DR itu selalu 409 ('berstatus delivered, bukan verified'). DR berstatus 'accepted' selamanya. Arah sebaliknya juga terbuka: harvest yang sudah masuk rute PLANNED (masih 'verified') masih bisa dilampirkan ke DR.
Langkah pengerjaan
Di dispatch: tolak harvest dengan delivery_request_id IS NOT NULL (409, sebutkan nomor DR).
Di submit_request: tambahkan syarat harvest tidak ada di RouteStop pada Route berstatus PLANNED/IN_PROGRESS (NOT EXISTS subquery) di UPDATE … WHERE yang sudah ada.
Di daftar collector/attachable-harvests: sembunyikan harvest yang sedang dijadwalkan rute.
Tambahkan tes di tests/test_factory_ops.py untuk kedua arah.
bad_dr = [h.id for h in harvests if h.delivery_request_id is not None]if bad_dr:    raise HTTPException(409, f"Harvest {bad_dr} sudah terlampir Delivery Request — kirim lewat QC, bukan rute.")
Selesai bila (kriteria uji)
Dispatch harvest terlampir DR → 409; melampirkan harvest yang sedang di rute → 409.
Tes lama tetap hijau di SQLite & PostgreSQL.
B2 · .env menunjuk PostgreSQL port 5432 (server lain) → aplikasi diam-diam jatuh ke SQLite
Prioritas: Sedang   ·   Lokasi: .env baris 2–3; app/config.py baris 11–12; docker-compose.yml (port 5433:5432)
Masalah
Container proyek dipetakan ke port 5433, tetapi .env dan default config memakai 5432. Di mesin ini port 5432 dipakai PostgreSQL lain, sehingga login gagal ('password authentication failed for user biochain') dan aplikasi otomatis memakai SQLite. Akibatnya jalankan.bat tidak pernah memakai PostgreSQL walau container hidup.
Langkah pengerjaan
Ubah .env (dan .env.example) ke port 5433, atau buat variabel PG_PORT yang dipakai keduanya.
Samakan default di app/config.py dengan .env.example.
Pertimbangkan: bila DATABASE_URL eksplisit PostgreSQL tetapi gagal login, hentikan start (error jelas) kecuali ALLOW_SQLITE_FALLBACK=true — fallback diam-diam menyembunyikan salah konfigurasi.
Selesai bila (kriteria uji)
Dengan container hidup, log start menampilkan PostgreSQL aktif (badge UI tidak lagi 'SQLite Lokal Aktif').
B3 · Tagihan rute di atas batas tolak mutu tercatat 'terutang' dengan Rp 0
Prioritas: Sedang   ·   Lokasi: app/services/factory_ops.py — settle_route
Masalah
Bila recommend_price mengembalikan accept=False (mis. kadar air ≥ batas tolak), harga diset 0.0 dan status 'terutang' Rp 0. Barang secara fisik diterima tetapi tagihan nol yang 'terutang' membingungkan dan bisa ditandai 'dibayar' Rp 0.
Langkah pengerjaan
Pilih satu aturan bisnis: (a) receive ditolak dan harvest diarahkan ke /factory/reject, atau (b) tagihan berstatus 'menunggu_harga' dengan catatan 'di luar batas mutu — perlu keputusan harga manual'.
Rekomendasi: (b) — pabrik tetap bisa menetapkan harga diskon lewat /settlements/{id}/price.
Tambahkan tes: harvest kadar air 30% lewat rute → tagihan bukan 'terutang Rp 0'.
Selesai bila (kriteria uji)
Tidak ada tagihan berstatus 'terutang' dengan amount_rp = 0 dari harga engine.
B4 · Teks dasar harga menampilkan 'kadar air None%'
Prioritas: Rendah   ·   Lokasi: app/services/factory_ops.py — settle_route (string basis)
Masalah
Bila harvest.moisture kosong, engine memakai kadar air referensi tetapi teks basis tetap mencetak harvest.moisture (None).
Langkah pengerjaan
Simpan nilai moisture yang benar-benar dipakai ke variabel, gunakan di teks basis dan kolom moisture tagihan.
Selesai bila (kriteria uji)
Teks basis selalu berisi angka, dan menyebut 'kadar air referensi' bila memakai default.
B. Celah keamanan & integritas data
S0 · Pengepul lain bisa menolak harvest hasil lelang milik pemenang (IDOR)
Prioritas: Tinggi   ·   Lokasi: app/routers/collector.py — POST /collector/reject (±baris 147–160); bandingkan dengan /collector/verify (±baris 101–102)
Masalah
Harvest hasil lelang dibuat berstatus 'reported' dengan collector_id = pengepul pemenang (app/services/trade.py ±baris 196). /collector/verify sudah menolak pengepul lain (403 'hasil lelang pengepul lain'), tetapi /collector/reject tidak memeriksa kepemilikan: pengepul mana pun yang tahu harvest_id bisa menolak harvest itu. Kontrak lelang batal dan collector_id ditimpa menjadi milik penyerang. transition() di app/services/custody.py juga tidak memeriksa kepemilikan. Ditemukan oleh tinjauan keamanan otomatis atas commit 5acf765, lalu dikonfirmasi lewat pembacaan kode.
Langkah pengerjaan
Di reject_harvest: muat harvest dulu; bila harvest.collector_id tidak kosong dan ≠ user.id → 403 (salin pola dari verify).
Lebih kuat: pindahkan cek ke transition() untuk semua tahap pengepul, agar endpoint baru tidak bisa lupa.
PostgreSQL: pastikan kebijakan RLS UPDATE harvests untuk peran pengepul mensyaratkan collector_id IS NULL OR collector_id = app_uid().
Tes: pengepul2 menolak harvest lelang milik pengepul → 403; harvest tetap 'reported' dengan collector_id semula.
harvest = await load_harvest(db, req.harvest_id)if harvest.collector_id is not None and harvest.collector_id != user.id:    raise HTTPException(403, "Harvest ini hasil lelang pengepul lain.")
Selesai bila (kriteria uji)
Tes IDOR lulus di SQLite & PostgreSQL; pemilik sah tetap bisa menolak.

S3 · Constraint tabel tagihan di model ≠ migrasi 011
Prioritas: Sedang   ·   Lokasi: app/models/factory_ops.py — CollectorSettlement.__table_args__; migrations/011_collector_settlements.sql
Masalah
Migrasi 011 punya ck_settle_status dan ck_settle_paid_ref (dibayar wajib punya nomor transfer), model tidak. Bila tabel dibuat lewat create_all (SQLite, atau PostgreSQL dengan AUTO_MIGRATE=true) dua aturan itu tidak ada, dan CREATE TABLE IF NOT EXISTS di migrasi tidak akan menambahkannya.
Langkah pengerjaan
Tambahkan kedua CheckConstraint ke model.
Di migrasi 012: ALTER TABLE … ADD CONSTRAINT … NOT VALID lalu VALIDATE CONSTRAINT (aman bila tabel sudah ada).
Buat tes yang membandingkan daftar constraint pg_constraint dengan model (mencegah drift ke depan).
Selesai bila (kriteria uji)
Tes drift lulus; insert 'dibayar' tanpa payment_reference ditolak di kedua DB.

T4 · computation_details untuk 5 engine lama
Prioritas: Sedang   ·   Lokasi: app/engines/quality.py (score_sample, baris 57–93), carbon.py (calculate_carbon_reduction, 44), forecaster.py (forecast_supply, 56), incentive.py (calculate_incentive, 45), blending.py (optimize_blend, 83–105)

Langkah pengerjaan
Ikuti format yang sudah dipakai app/engines/feedstock.py (±baris 176): method, references, inputs, steps, parameters_used.

Prakiraan: luas × produktivitas × rasio sekam × faktor musim per hari.
Insentif: pengali grade × bonus tier × syarat XP.
Blending: formulasi LP (fungsi tujuan, kendala spesifikasi), status solver, kendala aktif.
Tambahkan field computation_details: dict ke model Pydantic hasil (CarbonResult, ForecastResult, IncentiveResult).
Tampilkan di UI lab memakai komponen penjelasan yang sudah ada di kartu routing/pricing.
"computation_details": {    "method": "IPCC 2006 Vol.2 Ch.2 — substitusi bahan bakar",    "steps": [{"step": "Energi biomassa", "formula": "ton × HHV × η", "value": gj, "unit": "GJ"}, ...],    "parameters_used": ["karbon.husk_hhv_mj_kg", "karbon.boiler_efficiency", ...],    "references": ["IPCC (2006) Guidelines Vol. 2", ...],}
Selesai bila (kriteria uji)
Kelima endpoint mengembalikan computation_details dengan steps tidak kosong.
Tes: nilai langkah terakhir = nilai hasil utama (mis. net_reduction_tco2).
T5 · Generator nomor resi TRX sebagai fungsi database
Prioritas: Sedang   ·   Lokasi: app/services/trx_code.py — next_seq (baris 33); migrations/005_b2b_trade.sql (tabel trx_sequences, baris 55)
Masalah
Protokol B2B: 'Atomic Sequence Generator di database'. Sekarang atomik lewat UPSERT … RETURNING dari aplikasi (teruji 60 transaksi serentak), tetapi bukan fungsi database.
Langkah pengerjaan
Migrasi 012 (atau 013): CREATE OR REPLACE FUNCTION next_trx_seq(p_sender text, p_receiver text, p_yymm text) RETURNS integer LANGUAGE sql — isi UPSERT yang sama; opsional next_verification_code(...) RETURNS text yang memformat TRX-[PENGIRIM]-[PENERIMA]-[YYMM]-[SEQ].
GRANT EXECUTE ke biochain_app; rollback DROP FUNCTION.
trx_code.next_seq: bila dialek postgresql → SELECT next_trx_seq(...); SQLite tetap UPSERT lama.
Ubah test_trx_sequence_atomic_under_real_concurrency agar memanggil fungsi.
CREATE OR REPLACE FUNCTION next_trx_seq(p_sender text, p_receiver text, p_yymm text)RETURNS integer LANGUAGE sql AS $$  INSERT INTO trx_sequences (sender_code, receiver_code, yymm, last_seq) VALUES (p_sender, p_receiver, p_yymm, 1)  ON CONFLICT (sender_code, receiver_code, yymm) DO UPDATE SET last_seq = trx_sequences.last_seq + 1  RETURNING last_seq;$$;
Selesai bila (kriteria uji)
60 panggilan serentak ke fungsi → 1..60 tanpa celah; format kode tidak berubah; rollback bersih.

Selesai bila (kriteria uji)

T7 · Rencana rute jemput untuk tawaran yang dimenangkan pengepul
Prioritas: Rendah   ·   Lokasi: app/services/trade.py (farmer_transport_cost_per_kg baris 110, bid_advice baris 236); app/engines/routing.py; app/schemas/routing.py; app/routers/collector.py
Masalah
Protokol B2B Fase 2 meminta algoritma penjemputan untuk meminimalkan biaya per kg. Biaya angkut per kg baru dipakai sebagai saran saat menawar; belum ada rencana rute untuk tawaran berskema 'jemput' yang sudah diterima petani.
Langkah pengerjaan
Endpoint POST /api/v1/collector/pickup-plan (khusus pengepul): ambil tawaran diterima berskema jemput yang belum dijemput.
Depot = koordinat pengepul; titik = koordinat petani + kg diterima; kapasitas & biaya per km dari parameter grup logistik.
Panggil engine CVRP heuristik yang sudah ada (savings Clarke-Wright + perbaikan lokal) — jangan buat ulang.
Kembalikan urutan titik, km, total biaya, biaya per kg, dan computation_details dengan rujukan (Capacitated VRP; Clarke & Wright 1964).
UI kartu pasar pengepul: tombol 'Rencanakan jemput' + tabel urutan.
Selesai bila (kriteria uji)
Semua titik dikunjungi sekali, kapasitas tidak terlampaui, biaya/kg = total biaya ÷ total kg, latensi < 500 ms untuk 200 titik.
T8 · Skrip benchmark terpisah untuk semua engine
Prioritas: Rendah   ·   Lokasi: scripts/ (baru: benchmark_engines.py); saat ini hanya tests/test_routing.py::test_latency_slo dan loadtest/k6_double_submit.js
Masalah
Protokol algoritma meminta 'skrip pengukur waktu eksekusi (benchmarking)'. Pengukuran latensi baru ada untuk routing di dalam pytest.
Langkah pengerjaan
scripts/benchmark_engines.py: data tiruan berukuran bertingkat (routing 50/200/1000 titik, feedstock 10/100, blending, mutu 10.000 sampel, energi 24/120 bulan).

O1
tests/test_routing.py::test_latency_slo[1000-300] gagal 851 ms (batas 500 ms) saat mesin sibuk; lulus saat dijalankan sendiri.
Jalankan tes latensi terpisah (marker @pytest.mark.perf, dilewati di suite penuh) atau ukur median dari beberapa kali setelah pemanasan; benchmark resmi lewat T8.
O2
Suite penuh PostgreSQL 462 detik (sebelumnya 173 detik) dengan jumlah tes hampir sama.
Profil dengan 'pytest --durations=25'; kemungkinan pembuatan skema per tes (isolated_engine) + NullPool. Pertimbangkan skema per modul atau transaksi-rollback per tes.
O3
Cache parameter per proses disegarkan tiap 30 detik → antar worker gunicorn bisa berbeda hingga 30 detik setelah perubahan harga.
Pakai LISTEN/NOTIFY PostgreSQL atau versi parameter di Redis untuk invalidasi segera; minimal tampilkan 'berlaku ≤ 30 detik' di UI.
O4
Peringatan git 'CRLF will be replaced by LF' di hampir semua file.
Tambahkan .gitattributes (* text=auto eol=lf; *.bat eol=crlf) lalu git add --renormalize .
O5
Pekerjaan ada di branch master, sedangkan branch utama repo adalah main.
Buat PR master → main atau samakan nama branch sebelum kolaborasi.
O6
Teks lengkap protokol audit sirkular, SRE/chaos, dan asisten AI hilang dari transkrip (konteks diringkas); verifikasi ulang hanya berdasarkan ringkasan.
Tempel ulang ketiga protokol bila ingin dicek butir per butir secara literal.
O7
Laporan uang memakai basis akrual (bulan barang diterima); bulan pembayaran (paid_at) tidak dilaporkan.
Tambahkan kolom 'dibayar bulan ini' (basis kas) di laporan pengepul & pabrik bila diperlukan akuntansi.
O8
Daftar 'Tiba via rute' pabrik tidak menampilkan nama pengepul/petani; tabel tagihan hanya menampilkan nama pengepul.
Join ke users di /factory/arrivals; tampilkan petani asal di tagihan jalur rute.
